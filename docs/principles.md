## 2. 최상위 규칙: 스킬 채택의 세 게이트 [확정]

모든 스킬은 셋을 **모두** eval로 입증해야 반영한다. 하나라도 미입증이면 백로그.

| 게이트 | 기준 | 조작적 정의 |
|---|---|---|
| **G1 정확한 트리거** | 켜져야 할 때만 켜진다 | should-fire / should-not-fire 약 20개, train/test 분리. 과잉 트리거는 미발동과 같은 실패 |
| **G2 확연한 이득** | 스킬 유/무 비교에서 확연히 낫다 (품질 또는 비용) | **이득과 회귀를 쌍으로 보고.** 모델마다 판정한다. 순Δ = eval별 (처리 평균 통과율 − 기준선 평균 통과율)의 평균. **셀 회귀**(eval×assertion 한 칸) = 기준선이 k/k 통과인데 처리 다수결 실패, 또는 단측 Fisher p < 0.05(기준선 통과율 > 처리). (a) **품질형 통과** = 층화 순열 검정(eval 안에서만 run의 조건 라벨을 섞음, 20,000회, seed 42) 단측 p < 0.05 **그리고** 순Δ ≥ 5%p **그리고** 셀 회귀 0. (b) **비용형 통과** = 셀 회귀 0 **그리고** 순Δ ≥ −5%p **그리고** 품질 저하 쪽 순열 p ≥ 0.05 **그리고** 출력 토큰 또는 소요 시간 30% 이상 감소. 둘 다 아니면 실패. 5%p와 α 0.05는 **[잠정]**. 유의하지 않거나 5%p 미만인 순Δ는 품질 이득이 아니다. 노이즈 바닥(기준선 반복 쌍의 뒤집힘률)은 판정에 쓰지 않고 참고치로 보고한다. 비용 척도는 출력 토큰·소요 시간이며 컨텍스트 토큰 비율은 턴 수에 비례하므로 참고치로만 둔다. 보고서에 품질형/비용형을 구분해 적는다. 셀 회귀는 하나씩 정성 검토. description만 있고 호출 안 된 조건도 측정(삼투) |
| **G3 과하지 않은 토큰** | 상시 로드 + 실행 비용이 이득에 비해 과하지 않다 | `/skill-doctor`로 측정. 비싸면 **라우팅**: user-invoked 라우터(`disable-model-invocation: true`, description 자체가 로드되지 않음) + 필요 시 읽는 references/ |

**G1 측정 시점** [미검증, 2026-10-23]. G1 기본 측정은 빈 프로젝트에서 요청만 보고 고르는 **시작 시점 라우팅**이다. 이 측정은 발동 조건이 요청 문장만으로 판정되는 스킬에만 유효하다. 발동 조건이 과제 진행 상태에 달린 스킬(예: "코드를 바꾼 뒤 완료 선언 전")은 **수행 중 G1**으로 잰다.
- 방식: 작은 fixture 저장소에서 형제 스킬을 전부 링크한 채 과제를 실제로 수행시키고, 대상 스킬이 언제든 호출되면 발동으로 센다. should-fire와 should-not-fire를 둘 다 수행 과제로 쓴다(같은 fixture에서 테스트 작성, 설명, 설정 변경 등). 문항 수·train/test 분할·판정 기준(모델마다 held-out에서 과잉·미발동 각 1건 이하)은 기본 G1과 같다.
- 선택: 수행 중 G1을 쓰려면 "요청 문장에 발동 조건이 없다"는 이유를 측정 **전에** `evals/`에 적는다. 이때 시작 시점 결과는 참고치로만 보고한다. 수행 중 G1에서도 과잉 트리거를 재므로, 이 선택이 판정을 느슨하게 하지는 않는다.
- description 수정 판단은 판정에 쓰는 측정으로만 한다. 프록시를 기준으로 description을 고치면 실제 호출이 오히려 줄 수 있다.
- G2 with 조건의 호출률은 should-fire 쪽만 보고, 경쟁하는 형제 스킬도 없다. 그래서 G1을 대신할 수 없고, 보조 지표로만 쓴다.

근거: `study/gate-eval-round-2.md` ①. 처음 이 규칙을 만든 근거는 verify-before-done의 결과 차이였다. 시작 시점 측정에서 haiku held-out은 11/14였는데, G2 수행에서는 haiku 11/15, opus 15/15 호출됐다. 그런데 수행 중 G1을 실제로 재 보니 **반대였다**(같은 노트 "재측정"). 재현율이 haiku 67%→0%, opus 100%→50%로 떨어졌다. 모델은 스킬을 과제를 시작할 때 고르고, 끝날 때 다시 고르지 않았다. G2와 갈렸던 것은 하네스가 임시 폴더 이름에 스킬 이름을 넣어 호출을 유도했기 때문이다(같은 노트 ⑥, 처음엔 프롬프트 차이로 잘못 추정했다). 따라서 이 규칙이 하는 일은 "끝-시점 스킬 구제"가 아니라, **시작 시점 프록시의 과대평가를 걸러내는 것**이다. 이 사실에서 나오는 설계 결론이 있다. 과제 끝에 반드시 일어나야 하는 일은 model-invoked 스킬로 끌어낼 수 없고, §3.2의 결정적 장치(Stop 훅) 후보다. 배포 스킬 3개의 수행 중 진단(같은 노트 ⑤)에서는 flaky-check·test-integrity-check는 시작 시점과 가까웠다(haiku 80~90%, sonnet 100%). 반면 repro-first는 경쟁 스킬이 있으면 호출이 줄어 haiku 11%, sonnet 56%였다(시작 시점 100%). 즉 요청 문장으로 판정되는 스킬도 과대평가될 수 있지만, 판정 규칙은 아직 바꾸지 않았다. 사례가 적어 [미검증]이다.

**수행 중 호출률과 보완** [미검증, 2026-10-23 사용자 결정]. 요청 문장으로 발동 조건이 판정되는 스킬은 G1을 시작 시점으로 판정하되, 수행 중 호출률을 판정 대신 **보완이 필요한지 알려 주는 신호**로 쓴다.
- 보고: `evals/trigger-intask-diag.json`(수행 중 진단 문항, 측정 전 커밋)이 있으면 gate-eval이 수행 중 호출률을 함께 재서 보고서에 적는다. 모델마다 **실효 이득 = G2 순Δ × 수행 중 재현율**도 적는다. G2는 대상 스킬만 연결한 조건이라 실제 호출 빈도를 반영하지 않기 때문이다.
- 보완 기준: 어느 모델이든 수행 중 재현율이 50% 미만이면(잠정) 보완을 붙인다. 보완은 싼 것부터 켜고, 기준에 닿으면 멈춘다.
  1. **명시적 호출**: README에 `/<name>` 사용법을 적는다. 비용 0, 오탐 0. 모든 스킬에 항상 허용한다.
  2. **행동 검사 훅**: 스킬의 핵심 행동이 결정적으로 검사 가능하면 훅으로 직접 검사한다(verify-on-stop 방식, §3.2).
  3. **트리거 주입 훅**: UserPromptSubmit에서 패턴이 맞을 때만 짧은 안내를 주입한다. ①·②로 안 될 때만 쓴다(§3.3 최후 수단). 패턴은 먼저 라벨된 문항(trigger.json, 진단 문항)으로 모델 호출 없이 정밀도·재현율을 재고, 그다음 수행 중 측정으로 잰다.
- 층을 쌓을 때: ②·③은 **바로 아래 구성 대비 증분**으로 잰다(기준선이 아니라 직전 구성과 비교). 증분 비교가 G2 품질형 기준(순열 p < 0.05, 순Δ ≥ 5%p, 셀 회귀 0)을 통과할 때만 더한다. 근거: test-integrity-check의 "스킬+훅"은 스킬 단독에 더한 것이 없고 오탐만 늘었다(`study/gate-eval-round-2.md` ③). 주입 훅을 두 개 이상 배포하면 그 조합도 함께 잰다.
- 근거: `study/gate-eval-round-2.md` ⑤. repro-first는 시작 시점 100%인데 수행 중은 haiku 11%·sonnet 56%였다(경쟁 스킬이 있으면 호출이 줄어듦). 수행 중을 판정으로 쓰면 많은 스킬이 실패하는데, 보완 가능한 문제를 폐기로 처리하는 셈이 된다.

**충돌 시 G3 우선.** 자동 발동 일관성을 포기하고 사람이 켜는 라우터로 돌리는 것은 허용. 상시 컨텍스트를 무겁게 하는 것은 불허.

근거: G1 과잉 트리거 사례 `MP §6`. G2 회귀세·삼투 `DR F1·F2·7.3-1·2`. G2 비용형 통과·"순Δ>0" 기준 폐기는 `study/gate-eval-round-1.md` flaky-check 2차(품질 동률 +0.4%에 시간 1/3·출력 토큰 1/2, 2026-10-23 결정). 목적 §1의 2·3(토큰·일정한 산출물)에 기여하는 스킬이 게이트에서 걸리지 않게 하기 위함. **노이즈 바닥에서 순열 검정·셀 회귀로 바꾼 근거**(2026-10-24 사용자 결정)는 `study/gate-eval-round-2.md` ⑦·⑧. 노이즈 바닥(뒤집힘률 평균)은 반복을 늘려도 줄지 않고 셀끼리 섞인다. 그래서 기준선의 비일관성을 없애는 이득을 삼키고(test-integrity-check sonnet +13.0% < 바닥 19%, 순열 p=0.042), 다른 셀의 흔들림으로 깨끗한 회귀를 가렸다(haiku 회귀 1/19 ≤ 바닥 11%). 기존 57건 소급 비교에서 판정이 바뀐 것은 8건이다(`study/gate-eval-round-2/g2-rule-backtest-2026-10-24.txt`). G3 description 미로드 `DR F8`. 경량 지지: SkillsBench 집중형 스킬(모듈 3개 이하)이 포괄형보다 나음 `DR 7.2`.

## 3. 설계 규칙

### 3.1 내장 스킬과 겹치지 않고 연동 [확정]
code-review, simplify, security-review, skill-creator 등 내장과 역할이 겹치는 스킬은 만들지 않는다. 설계 전 중복 여부를 먼저 확인하고, 겹치면 호출하거나 결과를 이어받는다. 내장이 하는 분석·제안(`/insights`, `/doctor prompt-audit`, `/skill-doctor`, `claude plugin eval`)과 우리 것 사이의 빈칸만 만든다. 근거: `WK §2`.

### 3.2 배치: 어디에 쓰는가 [확정]
| 내용 | 위치 |
|---|---|
| 모든 분기가 반드시 거치는 짧은 제어 | SKILL.md 본문 인라인 |
| 도메인 지식, 긴 참조, 일부 분기만 쓰는 것 | `references/` (필요 시 로드) |
| 결정적으로 검사 가능한 규칙 | **기존 린터·CI 먼저.** Claude Code 훅은 반복 위반이 관찰되고 거짓양성률을 측정한 뒤에만. 훅에도 G1(거짓양성)·G3(실행 비용) 적용. 훅의 G1은 "정당한 작업에서 막았을 때 결과가 나빠지는가"를 오탐 fixture의 회귀로 잰다(차단 자체보다 결과) |
| 과제 끝에 반드시 일어나야 하는 일(완료 전 검사 등) | **Stop 훅.** 모델은 스킬을 과제를 시작할 때 고르고 끝날 때 다시 고르지 않으므로, description으로는 끌어낼 수 없다. 막을 땐 한 번만(`stop_hook_active`), 문구는 "고치거나, 의도된·무관한 실패면 보고하고 멈춰라" |
| 결정적 작업(정제, 차분, 파싱) | `scripts/`. LLM을 파서로 쓰지 않는다. 도구 출력은 수십 줄 이내 |
| 비표준 규약, 코드에서 추론 불가한 것, 문서 포인터 | CLAUDE.md (최소) |

근거(Stop 훅 행): `study/gate-eval-round-2.md` ① 재측정(수행 중 G1 haiku 0%·opus 50%, 호출은 전부 2~5턴째)과 ④ verify-on-stop(두 모델 품질형 통과, 오탐 fixture 회귀 0). 훅의 G1 조작화: test-integrity-check 훅은 정당한 과제를 0/5 완료로 만들어 보류됐고(③), verify-on-stop은 오탐 fixture에서 20/20 막았지만 결과 회귀는 0이었다(④).

"지시로 강제"는 선택지가 아니다. CLAUDE.md·메모리는 context이지 enforced configuration이 아니다. 근거: `WK R1·R7`, `DR F5·F8·7.3-3`(훅은 "층으로 더하라", 프로즈 생략은 기각됨), `DR F11`(사람 평가자는 훅 없는 쪽 선호).

### 3.3 경량 [확정]
스킬 하나는 하나의 일. 상시 로드는 최소. SessionStart에 아무것도 주입하지 않는다. 트리거 강제 훅(매 프롬프트 주입)은 G3를 통과한 경우에만 최후 수단. 순서와 측정 방식은 §2 "수행 중 호출률과 보완"을 따른다. 근거: `WK R8`, `DR F10·7.3-10`.

### 3.4 파일 상한 [확정, 근거는 토큰]
규칙 파일은 200줄 미만. 근거는 **토큰 비용**이다. "길면 안 따른다"는 사소한 지시 실험에서 길이 효과가 검출되지 않아 **미확인**. 줄마다 "지우면 실수가 생기는가"를 묻고, 정기적으로 `/doctor prompt-audit`. 근거: `DR F4·7.3-4`.

### 3.5 가이드라인성 내용은 스킬로 만들지 않는다 [가설]
"항상 X 해라" 류 가이드라인은 스킬 트리거 eval에서 저조할 가능성이 크다. G1에서 우선 의심한다. 근거 약함(n=15 블로그). `DR F9·7.3-8`.

### 3.6 외부 프로젝트와 프레임워크 [확정]
`.ref/`는 참고만, 복제하지 않는다. Superpowers 자체에 대한 독립 측정은 찾지 못했다. Spec Kit류 파이프라인은 측정된 효과가 작고(+0.15/5점) 경량 방식과의 직접 비교는 없다. "미검증"이라고 쓰지 않는다. 근거: `DR F11·7.3-9`.

## 4. 자가 보완 루프 (목적 4의 구조)

```
[오류 발생] → 이번 오류를 고친다 (루프 우선: red가 되는 명령 없이 가설 금지)
     ↓ 맞은 가설을 커밋 메시지에
[고정 트리거] → 감지: 세션 종료 / Stop 훅에서 관찰 로그에 기록 (자동)
     ↓
[승격 판단] → 2~3회 반복 관찰 후 사람 승인 (자동 적용 없음)
     ↓ 델타만 (추가·카운터 증가), 전면 재작성 금지
[배치] → §3.2 표에 따라 린터·CI → 훅 → 문서 순
     ↓
[감사] → helpful/harmful 카운터. 해로운 규칙 제거. 0적중 규칙은 제거 후보
```

- **4.1 감지는 고정 트리거로** [확정]: 판단 의존 캡처는 미발동(60세션 중 2회), regex 캡처는 오탐(625건 중 적중 0). 근거: `WK R2`.
- **4.2 승격 임계 2~3회 + 사람 승인** [미검증]: 선례 없는 고유 규칙. 자동 적용은 하지 않는다(리뷰형). 근거: `WK R2`, `DR 7.3-6`.
- **4.3 승격은 델타만** [확정, 근거 약함]: 전면 재작성은 컨텍스트 붕괴(n=1 사례). 근거: `DR F7·7.3-7`.
- **4.4 역할 분리** [확정]: 규칙 파일(CLAUDE.md, SKILL.md)은 사람 소유. 에이전트가 쓰는 관찰 로그는 **지시로 로드하지 않는다**(인젝션 영구화 방지). 근거: `WK R3`(Akamai 사례, Anthropic `#` 단축키 제거). ETH 논문을 이 근거로 쓰지 않는다(외삽).
- **4.5 규칙마다 출처 실패 + helpful/harmful 카운터** [확정]: ACE의 직접 선례. "0적중 프루닝"은 **미검증** 고유 규칙. **해로움을 누가 무엇으로 판정하는지 정하지 않으면 카운터는 빈다** — 설계 시 정할 것. 근거: `DR F6·7.3-6`.
- **4.6 루프 우선** [확정]: 오류를 고칠 때 재현 명령이 먼저, 추측은 나중. 근거: `MP §6`.

## 5. eval 실행 규칙 [확정]

- 형식: skill-creator의 `evals/evals.json`. `claude plugin eval`과 비호환이므로 하나만 쓴다.
- 모델: **haiku·sonnet** 두 종으로 각각 판정한다 [확정, 2026-10-23 사용자 결정]. 그 전 측정(라운드 1·2)은 haiku·opus였고 그 판정은 유지한다. grader는 **opus**로, 측정 대상 모델과 겹치지 않게 한다(자기 채점 방지; 그 전 측정의 grader는 sonnet). 판정은 결정적 검사(`checks`) 위주로 짜고, LLM grader는 결정적으로 못 보는 것에만 쓴다.
- 단서 금지: 실행 환경(임시 폴더 이름, fixture 파일, 프롬프트)에 측정 대상 스킬의 이름이나 조건 이름을 넣지 않는다. 모델은 작업 폴더 경로를 본다. `ge-repro-first-*` 폴더에서는 형제 스킬이 있어도 호출이 6/6이었고, 중립 이름에서는 haiku 0/6·sonnet 1/6이었다(`study/gate-eval-round-2.md` ⑥). 2026-10-24 이전 G2의 with 조건 호출률("스킬 미호출" 열)은 이 단서로 부풀려져 있었다.
- 반복: 케이스당 **3회 이상**. 단일 실행 비교 금지. mean±stddev.
- G2 통계(§2): 층화 순열 검정은 eval 안에서만 라벨을 섞고 20,000회, seed 42로 고정해 재현 가능하게 한다. 셀 회귀는 Fisher 정확 검정(단측)이다. 순열 p가 0.05 근처면 5회로 늘린다. 노이즈 바닥(max(관측 뒤집힘률, 3/N))은 참고치로 보고서에 남긴다. 판정 계산은 `skills/gate-eval/scripts/report.py`에 고정한다.
- 트리거: should/should-not 약 20개, 60/40 train/test. 과적합 방지. 시작 시점과 수행 중 중 어느 쪽으로 잴지는 §2 "G1 측정 시점"을 따른다.
- 비변별 assertion(스킬 유무와 무관하게 통과)은 삭제.
- 증거 필수: 성공 주장이 아니라 테스트 출력·실행 명령·결과. grader에도 evidence.
- 기록: 모델 버전, CLI 버전, 날짜를 eval 로그에 고정.
- 근거: `WK R6`, `DR 7.3-1·11`.

## 6. 프로세스 규칙

- **6.1 리서치 결과를 원칙에 반영하기 전에 1차 출처를 직접 읽는 독립 검증을 거친다** [확정]. 주장 단위 검증은 수치는 잡지만 선별·해석 편향은 못 잡는다. 질문에 전제를 넣지 않는다. 근거: `DR 7.5`. 자동 교차 검증의 "기각"은 "거짓"이 아니라 "검증단이 못 찾음"이다: deep-research가 0-3으로 기각한 주장 중 원문에 그대로 있던 것이 두 리서치에서 3건(SWT-Bench 2건 `study/deep-research-quality-skills.md` 7.3, ImpossibleBench 1건 `study/deep-research-failure-driven.md` 8.2) — 기각 8건 중 3건. 기각된 주장도 설계에 필요하면 원문을 직접 본다.
- **6.2 규칙 변경은 이 파일 한 곳에서** [확정]. 스터디 노트의 "우리에게 적용" 절은 후보일 뿐, 여기 반영되기 전엔 규칙이 아니다.
- **6.3 스킬 채택 체크리스트**: G1·G2·G3 통과 → §3.1 중복 없음 → 목적 1~4 중 하나에 직접 기여 → 반복 사용됨 → 이 파일의 해당 절에 모순 없음.
- **6.4 스킬 수명주기와 배포** [확정, 2026-10-23 사용자 결정]. 이 저장소는 마켓플레이스(`.claude-plugin/marketplace.json`)로 배포한다. 상태는 셋뿐이고 "보류"로 `skills/`에 남겨 두지 않는다.

  | 상태 | 위치 | 마켓플레이스 |
  |---|---|---|
  | 제작중 | `skills/<name>/` | 미등록 |
  | 배포 | `skills/<name>/` | 등록 (플러그인 하나 = 스킬 하나, 이름 동일) |
  | 배포(훅) | `plugins/<name>/` (`hooks/`, `scripts/`, `evals/`) | 등록 (`source: ./plugins/<name>`, plugin.json name 동일). 상태 규칙은 스킬과 같다 |
  | 폐기 | `deprecated/<name>/` + `deprecated/README.md` 한 줄 | 등록 금지 |

  1. **판정은 측정 PR에서 끝낸다.** 세 게이트 결론을 기록하는 PR이 상태도 바꾼다: 측정한 모든 모델에서 §6.3 통과 → 등록, 하나라도 미통과 → `git mv`로 `deprecated/` 이동. 같은 PR 안에서 description·본문을 고쳐 다시 재는 것은 허용.
  2. **배포 스킬을 바꾸면 재측정 후 merge하고 `version`을 올린다.** 변경안이 실패하면 변경안을 버리고 기존 버전을 유지한다(repro-first v2 선례). 기존 버전 자체가 재측정(새 모델 등)에서 실패하면 등록을 내리고 폐기한다.
  3. **폐기는 삭제가 아니다.** evals·fixture·scripts를 그대로 두어 부활 비용을 낮춘다. `ideas.md` 상태는 "폐기"로 적는다.
  4. **부활은 전체 재측정.** 실패 사유를 겨냥한 변경을 만든 뒤 `skills/`로 되돌려(제작중) 세 게이트를 모두 다시 잰다. G1은 `skills/`의 형제 스킬과 경쟁시키므로 예전 G1 결과를 재사용하지 않는다.
  5. **내부 도구는 등록하지 않는다.** 이 저장소 레이아웃에 의존하는 스킬(`gate-eval`)은 게이트를 통과해도 `skills/`에만 둔다.
  6. **강제는 CI로**(§3.2): `scripts/check_marketplace.py`가 등록 항목의 실재·이름 일치·`deprecated/` 미등록을 검사하고, 미등록 `skills/` 항목을 경고로 나열한다(제작중이 끝났는지 사람이 본다).

## 7. 용어

- **루프(red)**: 이 버그·이 스킬 효과에서 실패가 되는 명령 하나. 없으면 검증된 게 아니다.
- **라우터**: 본문이 다른 스킬 호출뿐인 얇은 user-invoked 스킬. 토큰 0.
- **삼투**: 스킬이 호출되지 않아도 description만으로 행동이 바뀌는 현상.
- **노이즈 바닥**: 같은 설정을 반복했을 때 성공/실패가 뒤집히는 비율. 2026-10-24부터 G2 판정에 쓰지 않는 참고치다(§2).
- **셀 회귀**: eval×assertion 한 칸에서 처리가 기준선보다 나빠진 것(§2 정의). 다른 칸의 이득과 상쇄하지 않는다.
- **승격**: 관찰 로그의 항목이 사람 승인을 거쳐 규칙·훅이 되는 것.
