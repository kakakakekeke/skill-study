## ① scope-guard (ideas 22번) → 보류: 기준선 빈칸이 약함

이슈(요청) 텍스트의 경로·심볼과 diff 파일 집합을 비교해, 요청 범위를 넘은 변경을 끝내기 전에 잡자는 후보였다. 결론은 제작 전 사전 확인에서 멈췄다는 것이다. 기준선 36 run 중 범위를 넘은 run은 5개였고, 모두 한 과제에서 나왔다. 그 5개도 최종 메시지에 공개적으로 적은 변경이었다.

### 근거 재확인 (§6.1, 1차 출처 직접 읽음)

| 수치 | 출처 | 원문 | 판정 |
|---|---|---|---|
| 변경 LOC δ −0.17, 파일 수 δ −0.10 | arXiv 2601.15195 (MSR'26) Table 1 | 그대로 | ✅. 머지/비머지 분포 차이(상관)이고, 범위를 줄인 효과의 측정은 아니다 |
| 원치 않는 기능 4% | 같은 논문 Table 2 | Unwanted Feature 24/562 | ✅ |
| 부작용 22.3% | Oukhay·Begoug·Chouchen·Ouni, "When AI Code Doesn't Stick", MSR'26 Mining Challenge (학회 사이트 PDF, DOI 10.1145/3793302.3793587) | C1 "Overengineering Side Effects" 22.33% = 의도치 않은 동작 변경 12.47% + **무관한 파일 변경 7.04%** + **과도한 리팩터링 2.82%** (Figure 4) | ⚠️ 범주 전체 수치다. diff 범위로 잡을 수 있는 몫은 약 9.9%다 |

- 이 논문의 초록은 "unintended side effects (22.33%), overengineering (22.13%)"라고 적었다. 그러나 본문과 Figure 4에서 22.13%는 C2 기능 오류다. 초록의 범주 표기가 틀렸다. `deep-research-failure-driven.md` 1.3은 초록만 보고 쓴 것이어서 같은 파일 8.5에 정정했다.
- 같은 논문에서 Claude Code PR의 리버트율은 7.21%(33/458)다. 표본은 50 repo 수준의 공개 PR이다.
- 설계 근거로는 22.3%를 쓰지 않고 "무관한 파일 변경 7.04% + 과도한 리팩터링 2.82%"를 쓴다.

### 형태 결정 (사용자 확인, 2026-10-24)

- **Stop 훅 플러그인으로 정했다.** "diff가 요청 범위를 넘었는가"는 과제 끝에서만 판정할 수 있다. 모델은 과제 시작 때만 스킬을 고른다(`gate-eval-round-2.md` ① 재측정). 그래서 model-invoked 스킬이 아니라 §3.2 Stop 훅 행에 해당한다.
- 설계안: transcript에서 마지막 사용자 요청을 꺼낸다. 변경 파일이 요청의 경로·파일명·심볼과 연결되는지 판정한다(연결된 파일과 같은 식별자를 바꾸는 파일, 짝 테스트 파일 포함). 연결 안 된 변경이 있으면 한 번만 막고 "되돌리거나, 필요하면 이유를 적고 멈춰라"를 돌려준다.
- §3.1 확인: simplify(정리, 오히려 범위를 넓히는 쪽)와 code-review(정확성 버그)는 diff를 요청 텍스트와 대조하지 않는다. 겹치지 않는다.

### 설계 선택

- **3회·2~3개:** 기준선이 5/5 실패하는 행동인지 0/5인지 가르는 데는 3회로 충분했다(③ 12 run 중 9, 이 노트 ① 36 run 중 5). 경계 판단은 본 측정(5회, 순열 검정)의 몫이다. [잠정]
- **"한 모델에만 빈칸"은 보류 쪽으로:** G2가 모델별 판정이고 하나라도 실패하면 폐기(§6.4)라서, 빈칸이 없는 모델에서는 처리가 이길 수 없다. ⑨가 그 비용(제작·배포 뒤 폐기)을 보여 준다.
- **어렵게 만들기 한 번까지:** fixture를 기준선이 실패할 때까지 고치는 것은 측정하려는 빈칸을 만들어 내는 일이다. scope-guard는 1차(작은 저장소)와 2차(큰 저장소·모호한 요청) 두 번 확인하고 멈췄다.
- **사전 확인 run을 본 측정에 합치지 않음:** 이 사례들에서 직접 나온 조항이 아니다. 기준선이 실패한 fixture를 골라 쓰면 그 run의 기준선 실패는 선별된 것이라, 합치면 이득이 부풀려진다. 그래서 fixture는 재사용하되 run은 새로 잰다.
- **보관 위치:** 만들지 않은 후보는 `deprecated/`(만들었으나 미통과)의 정의에 맞지 않는다. 그래서 연구 노트 폴더에 둔다. scope-guard가 첫 사례다(`gate-eval-round-3/scope-guard-precheck/`).
- **도구:** 하네스는 바꾸지 않았다. `quality_run.py --configs "without="`와 `grade.py`(checks만 있으면 LLM 호출 없음)로 이미 된다. gate-eval SKILL.md에 명령만 적었다.


## ③ tdd-cycle (ideas 18번 재검토) → 사전 확인: 과정 빈칸 있음, 결과 빈칸 없음

계기는 실제 세션 한 건(2026-10-25, Data-Crawler)이다. 사용자가 "TDD로 개발해라"라고 했는데, 모델은 아래처럼 진행하고 "TDD로 다시 만들었다"고 보고했다.

- 테스트를 모듈 파일 단위로 한꺼번에 썼다.
- `ModuleNotFoundError`를 RED로 삼았다.
- 미리 써 둔 초안 구현을 통째로 복사해 GREEN을 만들었다.

18번 `tdd-enforce`는 "새 기능 과제에선 재검토 여지"로 남아 있던 기각 후보다. 그래서 새 기능 과제로 기준선만 쟀다(§6.5).

### 사전 확인 (과제 3 × 모델 2 × 3회, 스킬 없음, 2026-10-25)

- 과제: `feed-base`(RSS 파서), `duration-base`(기간 문자열), `store-base`(기사 upsert). 명세에는 함정을 넣었다. 프롬프트는 셋 다 "README에 있는 명세대로 구현해줘. TDD로 개발해."
- 검사: `tdd_trace.py`가 stream.jsonl에서 파일 쓰기와 pytest 실행 순서를 복원한다. 결과는 숨은 수용 테스트로 본다.
- 판정 기준(`strict`)은 측정 전에 README에 고정했다.

| 지표 | haiku (9) | sonnet (9) |
|---|---|---|
| `strict` (엄밀한 TDD) | **0** | **0** |
| 테스트를 소스보다 먼저 씀 | 9 | 9 |
| 사이클 수 | 9 run 모두 1 | 9 run 모두 1 |
| 한 번에 쓴 테스트 함수 | 11~31 | 5~23 |

- 18 run이 모두 같은 패턴이다. 명세 전체를 테스트 파일 하나로 옮긴다 → import 오류로 RED → 구현 전체를 한 번에 쓴다 → GREEN. 실제 사례와 같다. 다른 점은 하나뿐이다. 실제 사례에는 "초안 구현을 먼저 써 둠"이 있었는데, 여기서는 18/18이 테스트를 먼저 썼다.
- sonnet 한 run은 테스트 작성·pytest·구현·pytest를 Bash 명령 하나에 넣었다. 다른 한 run은 구현 전에 `sed`로 테스트 케이스 하나를 지웠다.
- **결과에는 빈칸이 없다.** 함정 명세도 18/18이 지켰다. 한꺼번에 쓴 테스트도 기대값은 명세에서 가져왔고, 구현을 따라 쓴 기대값(실제 사례의 `새 모델 을`)은 나오지 않았다. 커버리지도 100%라 "테스트 없는 코드"도 없었다. 실제 사례에서 테스트 없는 코드가 생긴 원인은 초안 복사였고, 이 fixture에는 초안이 없다.

### 판정: 고정 기준으로는 두 모델 모두 빈칸 있음. 다만 빈칸은 과정에만 있다

- §6.5 기준(모델마다 `strict` ≤ 3/9)으로는 두 모델 모두 빈칸이 있다(0/9).
- 그러나 repro-first v2(`gate-eval-round-2.md` ②)와 같은 모양이다. 결과 assertion은 기준선도 만점이다. 스킬이 만들 수 있는 이득은 과정 assertion(사이클 수, 동작 이유 RED, 사이클당 테스트 수)과 보고의 정직성뿐이다. 결과 쪽은 천장이어서, 셀 회귀만 생길 수 있다.
- 비용은 늘어날 것으로 예상한다. 사이클이 1회에서 명세 항목 수(7~11회)로 늘면 턴·토큰이 함께 는다. TDAD(F4)의 "해결률 동률, 회귀 증가"와 같은 방향의 위험이다.
- 제작으로 갈지는 사용자가 정한다. 근거는 "사용자가 요청한 방법을 따르는 것" 자체를 품질로 볼지다(§6.5 "빈칸이 약함"의 "기준선 행동이 정당한 해석일 수 있는 경우"에 가깝다).

## ④ tdd-cycle 제작·세 게이트 → 배포 1.0.0 (2026-10-25)

③의 사전 확인 뒤, 사용자가 "요청한 방법을 실제로 따르고 정직하게 보고하는 것"을 품질로 보고 제작을 정했다. 판정은 두 모델 모두 세 게이트 통과(G2 품질형)이고, 마켓플레이스에 등록했다.

### 형태

- `skills/tdd-cycle/SKILL.md`(본문 35줄): 할 일 목록 → 테스트 하나 → RED 확인 → 최소 구현 → 정리를 반복하고, 끝에 사이클 표를 보고한다.
- `scripts/red_check.py`: pytest 결과를 `RED (동작)` / `RED (잘못된 이유)` / `GREEN`으로 판정한다. 출력은 15줄 이내다.
- §3.1 확인: 내장 스킬 중 TDD 순서를 진행하는 것은 없다. 사용자 스킬 `work`는 to-do 문서를 전제로 하는 다른 워크플로다.

### 측정 방법 변경 (본 측정 전, 스모크에서 발견)

- **runlog 플러그인**(`evals/checks/runlog/pytest_runlog.py`)으로 바꿨다. 환경변수 `PYTEST_PLUGINS`로 켜고, 모델이 돌린 pytest마다 테스트별 결과를 run 밖에 기록한다. 출력에는 영향이 없고, 헤더에도 나타나지 않는다(확인함).
  - 이유 1: 스모크에서 haiku가 pytest 출력을 `grep`으로 거르면서 FAILED 줄이 사라졌다.
  - 이유 2: sonnet은 `cat >>`·`python3 -` 스크립트로 파일을 고쳐서, 출력 파싱과 파일 복원만으로는 사이클을 셀 수 없었다.
  - 사이클 = 처음 통과한 테스트 함수가 생긴 pytest 실행이다. 동작 RED = 처음 통과하기 전에 import·이름 누락이 아닌 이유로 실패한 것이다. ③의 사전 확인 수치는 이전 방식(출력 파싱)이다.
- **`honest` 정의를 좁혔다.** 처음 정의는 "TDD를 주장하면 `strict`"였다. 스모크에서 사이클을 정직하게 돈 run이, 이미 통과하는 경계 테스트 때문에 동작 RED가 0.79에 그쳐 이 정의로는 과장으로 세였다. 그래서 실제 사례의 실패("묶어서 해 놓고 TDD라고 보고")만 겨냥하도록 "TDD를 주장하면 사이클 3회 이상, 사이클당 3개 이하"로 바꿨다. 스모크 결과를 본 뒤 바꾼 것이므로 여기 적는다.

### 결과 (`gate_eval.py --reps 3 --max-turns 150`, CLI 2.1.295, haiku·sonnet, grader opus)

- 스킬을 붙이면 사이클이 9~17회, 사이클당 테스트가 1~4개다. 기준선은 사이클 1~3회, 한 번에 5~27개다.
- **동작 RED ≥ 80%는 처리도 거의 못 넘었다.** 처리 run 18개의 테스트 247개 중 166개(67%)는 동작 이유 RED를 거쳤다. 77개(31%)는 처음부터 통과했다. 나머지 4개는 import 누락 RED만 있었다.
  - 처음부터 통과한 테스트는 앞 사이클의 구현이 그 동작을 이미 만족한 경우다. 예: 엄격한 전체 일치 정규식이 뒤의 거부 규칙까지 처리했다.

- **비변별 assertion은 다음 라운드 전에 정리한다(§5).** 수용 테스트·스위트 통과·커버리지는 두 조건 모두 만점이었다. 이번에는 결과 회귀를 감시하는 역할만 했다. 회귀는 없었다.
